# Lote B08 · Batallas, casos y testimonios

## Contexto

Lote B08 de `plan-iteraciones.md` (M, tras B05). Termina con: «Batalla con reintento; el caso libera testimonios y colección». Hoy el backend solo tiene `resolver-caso` (guarda puntaje, emite SUPERA_CASO y **completa el caso aunque falle**) y `GET /cuentas/{c}/testimonios` (código, título, estado). No hay batallas, colección ni pista. El contenido de batallas y casos (preguntas, problemas, presupuesto, profesionales) sigue en el front; el backend guarda estructura y resultados. No se toca el front: se exportan fixtures `ruta-*` y se anotan pendientes de interfaz.

## Modelo de datos (decisión de diseño a aprobar; lo nombra el plan del lote)

- `TipoActividad.BATALLA`; `TipoEventoUso.SUPERA_BATALLA` (ref. actividad) y `VISTA_TESTIMONIO` (ref. testimonio). `MODELOS_REFERENCIA` y la tabla de `motor.md` se actualizan.
- `ActividadDimension` (catálogo): `actividad_id`, `dimension_id`, único sobre el par. Son los tipos RIASEC del caso (uno o varios). Solo las actividades CASO pueden tenerlas: lo valida el cargador y una prueba de invariantes de datos (no cabe en un `CheckConstraint`).
- `ResultadoBatalla` (estado): `progreso_id`, `victoria`, `aciertos`, `preguntas`, `fecha_hora`; checks `0 ≤ aciertos ≤ preguntas`, `preguntas ≥ 1`.
- `ColeccionOcupacion` (estado): `cuenta_id`, `ocupacion_id`, `actividad_id` (el caso que la liberó), `obtenida_en`; único (`cuenta_id`, `ocupacion_id`).
- `Testimonio.pista` (Text, nulo).
- Ambas tablas de estado en `TABLAS_DE_ESTADO`. Una migración autogenerada y revisada. Se sigue `/cambio-modelo`.

## Backend

**Acciones** (`app/api/acciones.py`, servicio en `app/services/actividades.py` salvo testimonios):

- `POST /acciones/resolver-batalla` `{cuenta, actividad, victoria, aciertos, preguntas, fecha_hora?}` → `RespuestaAccion`. Exige disponible y tipo BATALLA (409 si no). Siempre guarda `ResultadoBatalla`. Si gana y no había ganado: completa (reutiliza `completar_progreso`, que ya emite COMPLETA_BLOQUE si toca) y emite SUPERA_BATALLA; si además `aciertos == preguntas`, VENCE_DESAFIO_INTACTO (ref. nula, ya existe y abre `t-ins-oculta`). Si pierde: crea el progreso EN_CURSO si no existe, sin eventos. Intentos tras ganar se guardan sin eventos (repaso). `completar-actividad` rechaza BATALLA con 409 como hace con CASO.
- `POST /acciones/resolver-caso`: agrega `ocupaciones: list[str] = []` (códigos de las acertadas; 422 si alguno no existe). **Cambio de comportamiento:** solo completa el caso si `puntaje ≥ puntaje_minimo` (alineado con el front, `forestFireCaseOutcome.ts`); si falla, queda EN_CURSO. Al superar, agrega a `ColeccionOcupacion` las que la cuenta no tenía. Responde `RespuestaResolverCaso` = `RespuestaAccion` + `ocupaciones_nuevas`. `test_resolver_casos.py` sigue válido (no afirma la completitud al fallar).
- `POST /acciones/ver-testimonio` `{cuenta, testimonio, fecha_hora?}` → `RespuestaAccion`. Solo estudiante; 409 con mensaje de bloqueo si está bloqueado (`exigir_disponible`). Emite VISTA_TESTIMONIO solo la primera vez.

**Consultas** (`GET`, un archivo por dominio):

- `/cuentas/{c}/batallas` (`api/batallas.py`, `services/batallas.py`, `schemas/batallas.py`) → `list[BatallaCuenta]`: `actividad`, `estado`, `intentos`, `superada`, `primer_intento` (`victoria`, `aciertos`, `preguntas`, `fecha_hora`, o `null`). El primer intento es el que cuenta para la métrica (B14).
- `/cuentas/{c}/casos` (`api/casos.py`, …) → `list[CasoCuenta]`: `actividad`, `titulo`, `dimensiones` (lista de códigos RIASEC, por el orden de la dimensión; vacía si no tiene), `estado`, `intentos`, `superado`, `ultimo_puntaje`, `mejor_puntaje`.
- `/cuentas/{c}/coleccion` (en `casos`) → `list[OcupacionColeccion]`: `ocupacion`, `titulo`, `caso`, `obtenida_en`.
- `/cuentas/{c}/testimonios` pasa de `ContenidoEstado` a `TestimonioEstado`: `codigo`, `titulo`, `estado`, `visto`, `pista` (solo si BLOQUEADA), `descripcion` y `enlace` (`null` si BLOQUEADA). Cambio de contrato: el front aún no lo consume («Todavía no (sin vista)»).

Para apoderado y orientadora, las listas salen vacías, como el resto. Lecturas agrupadas por cuenta y definiciones de la caché; prueba de presupuesto de consultas para `casos` y `batallas`.

## Datos (`datos/ruta.py`, todo `DATO DE PRUEBA`; el cargador interpreta tuplas nuevas)

- `t-batalla` BATALLA en T1, opcional (no altera el cierre de T1 ya probado), regla: COMPLETA_ACTIVIDAD `t-inicio` (que da `t-ficha`, la ficha de repaso).
- `DIMENSIONES_ACTIVIDADES` (actividad, dimensiones), varias por caso: `t-caso` → (`R`, `S`).
- `TESTIMONIOS`: `t-testimonio-1` (con pista) y `t-testimonio-2` (sin pista), ambos con regla SUPERA_CASO `t-caso` (solo se emite al alcanzar `puntaje_minimo`).
- Insignia provisional `t-ins-batalla` con SUPERA_BATALLA `t-batalla`, para probar que el siguiente paso se abre una sola vez. Se anota en `decisiones.md` como provisional: en B10 se reemplaza por la regla que abre `t-explorar`.
- `fijos.py` no cambia (las ocupaciones con código ya existen: `firefighter`, `paramedic`…).

## Pruebas

- `tests/integration/batallas/test_batallas.py`: perder, reintentar y ganar; SUPERA_BATALLA y el desbloqueo una sola vez; primer intento en el GET; victoria intacta → `t-ins-oculta`; 409 bloqueada, tipo incorrecto y `completar-actividad`; 422 `aciertos > preguntas`; atomicidad.
- `tests/integration/casos/test_casos.py`: fallar no completa; superar completa y libera los dos testimonios y la colección; ocupaciones repetidas no duplican; 422 ocupación inexistente; tipo RIASEC en `GET casos`; presupuesto de consultas.
- `tests/integration/testimonios/test_testimonios.py`: bloqueado muestra pista y oculta enlace; `ver-testimonio` 409 bloqueado, VISTA_TESTIMONIO una vez, `visto`.

- Escenario `test_ruta_corta.py`: perder y ganar `t-batalla`; fallar y superar `t-caso` con ocupaciones; ver `t-testimonio-1`; consultar casos, colección y testimonios.

## Decisiones confirmadas por el usuario

1. Insignia de prueba `t-ins-batalla`, provisional hasta B10 (anotada en `decisiones.md`).
2. Fallar un caso no lo completa; solo al alcanzar `puntaje_minimo` se completa y libera testimonios y colección.
3. Las ocupaciones se aceptan como las envía el front, validando solo que existan (422 si no); sin catálogo de ocupaciones por caso.
4. Un caso puede tener varios tipos RIASEC: tabla `ActividadDimension` en vez de `Actividad.dimension_id`; `GET casos` devuelve `dimensiones`.
